# 公共工程规则

对所有支持的语言应用本规则。语言专属规则可以细化要求，但不能降低正确性或安全性标准。

## 范围与优先级

- 将用户明确要求和仓库指令视为最高优先级。
- 将格式化器、静态检查器、编译器、生成代码规则和 CI 配置视为可执行规范。
- 在安全且有意为之的情况下保持现有局部风格。
- 仅清理任务涉及的代码，避免全仓库格式化变更。
- 修改生成器、Schema 或模板，不要手工编辑生成产物。
- 引入新语法或 API 前确认项目支持的语言及运行时版本。

## 设计与可读性

- 使用能表达领域含义的名称，避免晦涩缩写、类型编码命名和误导性单位。
- 保持函数和模块职责集中、依赖明确、可变状态所有权范围清晰。
- 优先使用直观控制流和标准库能力，避免炫技式简写。
- 删除因本次任务失效的死代码，不保留被注释掉的旧实现。
- 注释不变量、限制条件、权衡和不明显的意图，不复述语法。
- 除非任务明确要求破坏性变更，否则保持公共 API 和序列化数据兼容。

## 数据、错误与资源

- 在系统边界验证不可信输入，并针对输出目标进行安全编码。
- 在影响行为时明确单位、时区、Locale、精度、舍入、可空性和可选性。
- 不静默吞掉错误；保留原始原因并补充上下文，但不得泄露敏感信息。
- 使用结构化清理机制和确定性的资源生命周期。
- 为网络、进程、锁和重试操作设置明确超时与取消行为。
- 当外部输入可影响资源消耗时，限制队列、重试、载荷、并发和内存增长。

## 安全与隐私

- 不提交密钥，也不记录凭据、令牌、会话标识、个人数据或完整敏感载荷。
- 使用参数化数据库操作和安全进程 API，不将不可信文本拼接为可执行命令。
- 在服务端操作或资源边界执行授权校验，不能只依赖 UI。
- 使用受维护的密码学库和安全随机数，不自行设计加密方案。
- 在相关边界防止路径穿越、不安全反序列化、注入、SSRF 和开放重定向。
- 新增依赖时检查必要性、维护状态、许可证、版本兼容性和已知风险。

## 测试与验证

- 测试可观察行为、边界、失败路径和本次变更修复的回归问题。
- 测试应确定且隔离于真实时间、随机数、网络和共享全局状态；显式集成测试除外。
- 按最小有效范围运行仓库的格式化器、静态检查、类型检查、单元测试、集成测试和构建。
- 未实际成功运行的检查不得宣称通过；无法运行时说明准确限制。
- 审查优先级依次为：正确性和安全性、兼容性、可靠性、测试、可维护性、可自动执行的格式规范。
