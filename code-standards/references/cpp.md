# C++ 开发规则

先读取 `core-engineering.md`。以仓库声明的 C++ 标准、构建配置、clang-format 和静态检查为准；没有项目规范时参考 Google C++ Style Guide。Google 当前指南面向 C++20，但不得因此向旧版本项目引入不兼容特性。

## 源文件与头文件

- 通常为每个 `.cc` 提供对应 `.h`；测试和只含 `main()` 的小文件可例外。
- 头文件必须自包含、可独立编译并使用项目路径派生的唯一 include guard；仅用于被包含的非自包含片段才使用 `.inc`。
- 直接包含所使用符号的声明，不依赖传递 include；避免为了前置声明而制造脆弱依赖，禁止前置声明不归项目所有的类型或 `std` 实体。
- 公共头文件只放必要接口。短小函数、模板和必须暴露的 `constexpr` 定义可在头文件；较长实现放入 `.cc` 或明确的内部区域并满足 ODR。
- include 顺序为：关联头文件、C 系统头、C++ 标准库头、第三方头、项目头；非空组之间空一行，组内按字母排序。
- 不使用相对父目录别名拼 include 路径；平台条件 include 保持局部。

## 作用域、声明与命名空间

- 除极少数情况外，将代码置于项目唯一命名空间；禁止 `using namespace`，禁止向 `std` 添加声明。
- `.cc` 中不对外使用的实体放入匿名命名空间或赋予内部链接；头文件中不得使用匿名命名空间。
- 不为聚合静态函数而创建无状态类；非成员函数放入合适命名空间。
- 变量在最窄作用域、最接近首次使用处声明并初始化；避免先声明后赋值。
- 全局变量应极少使用；必须明确初始化顺序、所有权和线程安全。优先常量、函数局部静态或受控依赖注入。
- 公共 API 中的类型、生命周期、单位和所有权应在签名处清晰可见。

## 类、所有权与特殊成员

- 优先组合而非实现继承；用于多态删除的基类析构函数必须为 public virtual 或 protected non-virtual。
- 单参数构造函数和转换运算符通常声明 `explicit`；禁止产生意外隐式转换。
- 资源拥有型类遵循 Rule of Zero；必须自定义时，成套审查复制、移动、赋值和析构。
- 使用 RAII 管理内存、锁、文件和句柄；应用代码避免裸 `new`/`delete`。
- `std::unique_ptr` 表示唯一所有权，`std::shared_ptr` 仅用于真实共享所有权；非拥有型访问使用引用、指针或项目约定的 view 类型。
- 不返回指向临时对象、局部变量或生命周期不明存储的引用、指针、iterator、view 或 span。
- struct 用于被动数据聚合；具有不变量、封装或复杂行为时使用 class。
- 成员初始化使用构造函数初始化列表或类内初始化，避免构造后再赋值。

## 类型与语言特性

- 优先使用固定语义的标准整数类型或领域类型；检查有符号/无符号比较、缩窄转换和溢出。
- 使用 `nullptr`，不使用 `NULL` 或整数 0 表示空指针。
- 使用 C++ cast；避免 C 风格 cast。`reinterpret_cast` 必须局限于经过审查的底层边界。
- `auto` 仅在类型明显、避免重复或迭代器/模板类型过长时使用；不得隐藏重要的数值宽度、所有权或业务类型。
- 常量优先 `constexpr`，只读对象使用 `const`；保持 const-correctness。
- 模板、概念和元编程应解决真实复用问题，限制错误复杂度与编译成本；能用普通函数或类型完成时不增加模板技巧。
- 宏仅用于 include guard、条件编译或无法由语言特性替代的场景；宏名使用项目规定的大写形式并避免重复求值。
- 运算符重载只在语义自然且不令人意外时使用；保持与对应运算和标准约定一致。
- 异常、RTTI、协程和模块遵循项目策略，不在局部代码擅自改变全局机制。

## 函数、控制流与错误

- 函数保持单一职责；输入参数优先值或 const 引用，输出优先返回值，避免含义不明的输出参数。
- 按值接收并移动仅在确实需要取得所有权时使用；移动后对象只执行契约允许的操作。
- 所有分支和 switch case 都应明确；有意 fall-through 使用标准属性和说明。
- 不使用 `goto` 组织普通控制流；清理由 RAII 完成。
- 错误处理遵循项目统一模型：异常、status/result 或错误码不得随意混用；保留上下文且不重复记录。
- 对边界、索引、迭代器、解析、算术、系统调用和并发结果进行检查。

## 并发与性能

- 共享可变状态必须有明确同步策略；锁的顺序、粒度和所保护数据应可审查。
- 使用 RAII 锁类型；等待必须有谓词并考虑虚假唤醒、超时、取消和关闭。
- 不分离线程而丢失生命周期；线程、任务和回调捕获对象必须活到执行结束。
- 原子操作必须说明内存顺序；不确定时使用默认顺序，不为微优化使用宽松顺序。
- 先以基准和 profile 证明性能问题，再引入缓存、内存布局或无锁复杂度。
- 对性能优化记录前置条件，并保持可测试的正确实现或验证方法。

## 命名、格式、注释与验证

- 文件、类型、变量、函数、常量和宏遵循仓库命名；同一 API 内保持一致，不编码类型信息。
- 使用 clang-format 或项目格式化器，不手工争论可自动决定的空白与换行。
- 注释解释所有权、线程安全、不变量、单位、算法选择和复杂度，不复述代码。
- 公共声明记录契约、失败方式和生命周期；实现细节写在实现附近。
- 启用项目规定的编译器警告并将新增警告视为错误；运行 clang-tidy、sanitizer 和单元测试等已有检查。
- 重点验证越界、use-after-free、数据竞争、整数溢出、异常安全、ABI/API 兼容和平台差异。
